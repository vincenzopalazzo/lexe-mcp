# Plan: x402 `exact` / `lnbtc` payer

Goal: an agent that already holds the caller's Lexe credentials can settle an
x402 Lightning challenge and hand back the `PaymentPayload` the resource
server expects. This is a **payer**. It does not put HTTP 402 back in front
of this MCP, and it does not revive the v2-removed L402/AgenticMail hop.

Trigger: [Atlas21, 25 Sep 2026](https://x.com/Atlas21_eng/status/2103479939114717601)
([article](https://atlas21.com/block-adds-lightning-to-the-x402-standard/)).
Block joined the x402 Foundation and landed Lightning as
[`exact` on `lnbtc`](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_lnbtc.md)
([#2861](https://github.com/x402-foundation/x402/commit/6fe0d4bfd104e8c61ae0b6aeaefe9da506d502ff),
benthecarman, 2026-09-23). Protocol version is x402 v2.

`main` at the time of this plan: `2a44a46` (2026-09-22, distroless GHCR image),
even with `origin/main`.

## What the scheme actually requires

`scheme = "exact"`, `asset = "BTC"`, `paymentFlow = "upfront"`,
`assetTransferMethod = "bolt11"` (default when omitted).

| Network | CAIP-2 | BOLT11 HRP |
|---|---|---|
| mainnet | `lnbtc:000000000019d6689c085ae165831e93` | `lnbc` |
| testnet | `lnbtc:000000000933ea01ad0ee984209779ba` | `lntb` |

`amount` is a positive integer **millisatoshi** string (`"25000"` = 25 sats).
`payTo` is the receiver's compressed secp256k1 node id, 66 lowercase hex.
`extra.invoice` is a fresh BOLT11 whose description hash is the SHA-256 of a
JCS (RFC 8785) request binding (`http:1` or `mcp:1`), whose expiry equals
`maxTimeoutSeconds`, and whose signing key equals `payTo`.

The client pays that invoice, checks `SHA-256(preimage) == payment_hash`, and
returns:

```json
{
  "x402Version": 2,
  "accepted": { "...the requirement, invoice byte-identical to the one paid..." },
  "payload": { "preimage": "<64 lowercase hex>" }
}
```

The resource server then calls its facilitator `/settle`. We do not implement
`/verify` or `/settle`, and we do not keep the replay store. A preimage is
bearer proof: never log it.

## What the node already gives us

Pinned reading of lexe-public `bcabbd3` (same pin as v2):

- `POST /user/v1/pay_invoice` plus the existing poll already moves the money.
  `BasicPayment` has had `preimage` (and `hash`) since node-v0.9.5. `lexe.pay`
  already returns the raw payment object, so a settled invoice pay may already
  contain `preimage`. A node that omits it cannot be used for this scheme
  (`invalid_exact_lnbtc_payer_preimage_required`). Do not submit a second pay.
- `POST /user/v1/create_invoice` accepts `expiry_secs`, `amount` (Lexe `Amount`,
  a sats decimal string; `1` msat = `"0.001"`), and `description_hash`.
  Description and description hash are mutually exclusive. The node sets the
  invoice `n` tag to `channel_manager.get_our_node_id()`, which is `NodeInfo.node_pk`.
  `description_hash` on the wire is `Option<[u8; 32]>` with no hex wrapper, so
  the JSON body is a 32-number array unless a probe proves otherwise.
- `GET /user/v2/node_info` → `node_pk` for `payTo` when we issue.

`payMaxSats` still applies. Compare millisatoshis to `payMaxSats * 1000`.
`0` remains “no cap”.

## Role

Phase 1 is the payer tool. Phase 2 is invoice issuance for a resource server
that uses the **caller's** node as its receiver. Both stay per-request Bearer
credentials. This process never holds a shared receiver key, which is what the
spec's receiver-key isolation rule needs.

Out of scope: facilitator, replay store, EVM/SVM x402, BOLT12 as an x402 asset
(the scheme is BOLT11 only), LNURL, bringing L402 back.

## Phase 1 — `lexe.x402_pay`

New tool. `lexe.pay` stays a raw Lightning pay and does not grow x402 fields.

Arguments:

- `requirements` — one `PaymentRequirements` object (the `accepts[]` entry the
  caller chose).
- `request` — the operation being bought, so we hash it ourselves:
  - HTTP: `method`, absolute `url`, optional raw `body_base64` (empty if
    omitted), `headers` map. Bound names come only from
    `requirements.extra.requestBindingParams.headers`.
  - MCP: `server` (absolute URI), `name`, `arguments` object, optional `_meta`
    object. Bound names come only from
    `requirements.extra.requestBindingParams.metadata`.
- `note?` — existing personal-note clip. Not part of the binding.

The profile in the requirement picks which shape is required. `mcp:1` on an
HTTP binding, or the reverse, is a client reject **before** `pay_invoice`.

Before paying, in order (spec “Client Payment Construction”):

1. `scheme`, concrete network, `asset == "BTC"`, positive integral `amount`
   and `maxTimeoutSeconds`, `payTo` = 66 lowercase hex that decodes as a
   compressed secp256k1 point.
2. Network must match `lexeNetwork` (`mainnet` ↔ the mainnet id and `lnbc`;
   `testnet3` ↔ the testnet id and `lntb`). A mismatch is an error, not a pay.
3. `paymentFlow == "upfront"`. Missing `assetTransferMethod` means `bolt11`;
   anything else is rejected.
4. Decode the invoice (bech32 + tagged fields). Require exactly one `h` tag,
   no `d` tag, amount in msat equal to `amount`, currency matching the
   network, `x` (expiry) equal to `maxTimeoutSeconds`, creation time ≤ now +
   skew (default 60s), and not expired.
5. Rebuild the JCS binding from `request` plus the requirement's profile
   params. SHA-256 must equal both `extra.requestHash` and the invoice `h` tag.
   HTTP also requires `PaymentRequired` resource URL when the caller passes
   `resource_url`; if they pass it, it must equal the bound URL.
6. `payTo` must equal the invoice `n` tag.
7. Cap check, then the existing `pay_invoice` + poll path. Amount passed to
   the node is the invoice amount in sats (`msat/1000` as a decimal string,
   no rounding). Routing fees are the node's problem and are not compared to
   `amount`.
8. On `completed`, require `payment.preimage` (64 lowercase hex, 32 bytes)
   with SHA-256 equal to the invoice payment hash (`p` tag, cross-check
   `payment.hash` when present). Return the payload. On `failed`, return
   `exact_lnbtc_payment_not_paid` with the index. On still-pending past the
   poll cap, return `exact_lnbtc_payment_in_flight` with the index and tell
   the caller to use `lexe.check_payment`, not a second `lexe.x402_pay`.

Result (`isError: false` only when the payload is safe to present):

- `settled`, `index`, `payment` (unchanged shape)
- `x402`: `{ "x402Version": 2, "accepted": <requirements with the paid invoice>, "payload": { "preimage": "..." } }`
- `payment_signature`: standard base64 of the JSON `x402` object, for a
  `PAYMENT-SIGNATURE` header. No extra whitespace re-encoding of `accepted`
  beyond the object the caller passed, with `extra.invoice` left byte-identical.

Stable `error` strings are the spec's client reasons (`invalid_exact_lnbtc_*`,
`exact_lnbtc_payment_in_flight`, `exact_lnbtc_payment_not_paid`). Gateway
failures stay `isError: true` tool results, same as `lexe.pay`.

### BOLT11 signature gap

The spec says: if `n` is absent, recover the signing key from the invoice
signature and require it to equal `payTo`. Go's stdlib has no secp256k1, and
this repo cannot take a `go.mod` dependency.

Phase 1 **requires the `n` tag** and rejects invoices that omit it
(`invalid_exact_lnbtc_invoice_payee_mismatch` is the wrong reason; use a local
reason `invalid_exact_lnbtc_invoice_payee_recovery_unsupported` and do not pay).
Lexe-issued invoices set `n`. Foreign invoices that rely on recovery are
refused rather than trusted. Signature verification of invoices that do carry
`n` is the same gap: phase 1 checks the tag, the node still rejects an invoice
it will not pay, and a later change can add verification without a new tool.
Do not vendor a secp256k1 stack in this change.

### JCS

A small stdlib canonicalizer, used only for the binding object and for
`_meta` value hashes (`0x01 || UTF8(JCS(value))`, or `SHA-256(0x00)` when
absent). Reject duplicate keys and non-JCS numbers we cannot serialize
exactly. Cover it with the spec's own vectors:

- HTTP article A → `0d6623f775e025501fa7f0a30b54da25aad62b6ccfe35c85da38016711e6c018`
- HTTP article B → `4a99860f75eed1ea8178a5db488e044173bc570c8a6210f2c8590cdf8622d509`
- MCP `get_article` / `{"article":"A"}` → `03941bfedc6af8a09b2f459fe83470284a76a8c75801caa9e1487a9276a693f4`
- article B, `delete_article`, and the other-server digests in the spec
- absent metadata `6e340b9cffb37a989ca544e6bb780a2c78901d3fb33738768511a30617afa01d`
- present `null` `c58dcb77cee9027d1f4b3207bd876d232e61f79ee9f9dbd4e6d834778da78b16`

Member order and whitespace must not change the digest. The invoice in the
spec is a test vector for field layout; do not pay it.

## Phase 2 — `lexe.x402_invoice`

Only after phase 1 is green. Issues a challenge skeleton from the caller's
node. The caller (a resource server they run elsewhere) still owns request
binding, facilitator settle, and the replay store.

Arguments: `amount_msat`, `expiry_secs` (1 … 7 days, the node's
`MAX_EXPIRATION_SECS`), `request_hash` (64 lowercase hex). No description
string.

Call `POST /user/v1/create_invoice` with `expiry_secs`, `amount` = msat/1000
as a sats decimal, `description_hash` = the 32-byte array. Read `node_pk`
from `node_info` and return a `PaymentRequirements` object:
`payTo = node_pk`, `extra.invoice` = the invoice, `paymentFlow = upfront`,
network from `lexeNetwork`. The caller fills `requestBindingProfile` and
`requestBindingParams`; we do not invent them.

Hermetic test: fake node asserts the JSON shape of `description_hash` and
that `amount` is the sats decimal. If a real node rejects the number-array
encoding, switch to the encoding it accepts and lock that in the test.
Do not guess hex.

- `server.go` — tool schema, `lexe.x402_pay` branch, BOLT11 tag parser next

- `server_test.go` — JCS vectors, invoice tag checks, network mismatch,
  msat↔sats, cap, missing preimage, in-flight index. No live gateway.
- `gateway_test.go` — one fake-node case: `pay_invoice` body is the invoice
  string, completed payment includes `preimage`, tool result contains
  `payload.preimage` and does not log it.
- `README.md`, `AGENTS.md` — one row for the new tool. State that L402 stays
  gone and this tool is the x402 payer.

## Edge cases

- Sub-sat amounts (`amount` not divisible by 1000) are valid on the wire.
  Send a fractional sats string (`"0.001"`). Do not round.
- Overpay on the Lightning side is the node's business. We still report the
  invoice amount. No refund tool.
- Same invoice presented twice: the node will not pay it twice. Surface the
  existing payment index if the poll finds it; do not mint a second payload
  from a payment that is not `completed`.
- `lexe.pay` of the same invoice remains available. Document that x402 callers
  should use `lexe.x402_pay` so the binding is checked before money moves.
- Clock: use `time.Now().Unix()`. Skew constant 60, not configurable in v1.
- Preimage in logs: the pay error truncates node bodies at 300 chars. A
  failed `create_invoice` / payment body that echoes a preimage must be
  redacted before that truncate. `lexe.pay` responses already include
  `payment` for the caller; that is the caller, not a log line.

## Test plan

`go vet`, `go test`, `go build`. CI smoke stays as it is (discovery and the
identity guard). No live Lexe call in CI.

Size: phase 1 is the BOLT11 tag parser plus JCS plus one tool (~a few hundred
lines, mostly tests). Phase 2 is a thin `create_invoice` wrapper. Branch:
`feat/x402-lnbtc`. Ship phase 1 on its own; phase 2 only if a resource server
is actually going to call it.
